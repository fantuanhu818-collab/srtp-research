# occupation_id V4.1全量构建说明

## 1. 这次完成了什么

团队完成了300条独立样本的人工复核。程序先把复核结果整理成结构化金标准，再将其中能够推广的反馈写入职业分类规则，最后重新构建2018—2025年全样本的职业类型变量。

V4.1仍使用原来的37个职业大类，不增加新的大类，也不使用“初级分类”强行填补无法判断的岗位。

## 2. 人工验证结果

- 300条全部完成复核，没有重复来源记录ID或空白职业代码；
- 第一环节“标准职业名称”正确267条，准确率89.00%；
- 第二环节“37类职业代码”正确271条，准确率90.33%；
- V4已经分类的270条中，职业代码全部正确；
- 主要问题是Z99覆盖不足：30条Z99中有29条能够经人工判断归入37类，1条继续保留Z99。

这说明V4的主要改进方向是增加可靠的职业名称别名和上下文规则，而不是放宽模糊匹配阈值。

## 3. V4.1如何吸收反馈

新增规则分成两类：

1. 标题本身足够明确时，使用职业名称别名。例如党群主管、爬虫工程师、网络推广经理、HRIS主管、农场技术员和宽带装维等；
2. 标题过于宽泛时，必须结合职位描述。例如区域助理、技术工程师、分公司副经理、计划员、验证工程师、设备运维和实施运维等。

“实施运维”在复测中曾出现边界冲突。V4.1最终规定：只有描述中出现实施方案、现场部署、客户培训、医疗信息化等证据时，才归入D06；普通服务器、终端和网络运维仍归D05。

## 4. 三层验证结果

1. 原1,038条确认人工样本全部通过，没有旧问题回归；
2. 300条人工反馈在V4.1中全部得到正确解释，且原来已正确的271条没有退化；
3. 2018—2025年全量5,235,398条记录全部通过行数、主键、代码范围、一级分类和版本一致性检查。

修订后的300条一致率只能称为“反馈修复检查”，不能再当作独立准确率。对V4真正独立的结果仍是修订前的90.33%。

## 6. 文件位置与使用方法

全量职业特征表位于：

`D:/SRTP/工作数据/features/occupation_v0.4.1/`

每个年度一个Parquet文件，使用`source_record_id`与回归底表连接。正式回归使用的核心字段是：

- `occupation_id`：37类职业代码，无法可靠判断时为Z99；
- `occupation_name`：职业大类中文名称；
- `occupation_standard_name`：程序识别出的标准职业名称；
- `occupation_method`：本条记录采用的分类方法；
- `occupation_confidence`：置信度；
- `occupation_review_flag`：是否建议继续复核；
- `occupation_version`：规则版本。

V4.1没有覆盖清洗数据、核心变量底表或V3职业特征表。下一步可以按`source_record_id`把V4.1的`occupation_id`合并到基准回归数据集。
