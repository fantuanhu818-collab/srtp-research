# `occupation_id`粗分类与模糊匹配方案 v0.3

状态：2022年已试运行，程序验证通过，待人工复核

制定日期：2026-11-16

适用底表：`D:\SRTP\工作数据\features\confirmed_core_v2`

## 先说结论

本项目基准回归不直接使用《职业分类大典》的449个职业小类，也不把每条招聘广告强行匹配到某一个官方职业细类。

正式职业变量回到项目原先的较粗分类：

- `occupation_l1`：10个职业大类，例如数字技术、市场销售与运营、生产质量与供应链；
- `occupation_id`：37个职业组，例如软件开发、销售、财务会计与审计、生产制造与工艺；
- `Z99`：无法从岗位名称可靠判断的“其他/待分类”。

《职业分类大典》和模糊匹配仍然有用，但只作为**帮助补充原有规则的工具**：帮助我们把“写法不规范、带有少量噪声、但职业含义比较明确”的岗位补进37个职业组。它不再直接决定基准回归的职业类别。

## 一、为什么要这样改

2022年有328,548条招聘广告：

|方案|最终分类层级|已分类记录|覆盖率|
|---|---|---:|---:|
|v0.1 原关键词规则|项目自建37个职业组|231,619条|70.50%|
|v0.2 职业大典匹配|职业大典小类|174,033条|52.97%|

v0.2覆盖率更低，不是程序失败，而是职业大典小类对在线招聘标题来说过细。招聘标题常写“研发工程师”“技术员”“项目经理”，但只看标题无法判断它究竟对应哪一个细小官方职业。因此，不能为了“使用官方分类”而牺牲可解释性和覆盖率。

本研究中，职业变量的主要任务是控制不同职业之间本来就存在的工资差异。对于这个任务，37组比449个小类更合适：它能区分软件开发、销售、财务、生产等主要工作，又不会把样本切得过碎。

## 二、最容易理解的做法

可以把职业分类理解为“先看懂，再补漏”：

```text
原始招聘岗位
    ↓
清理广告词、地点和职级词，保留原文
    ↓
原关键词规则能明确判断吗？
    ├─ 能 → 直接归入37个职业组
    └─ 不能 → 与职业名称词典做精确/模糊匹配
                    ↓
              结果足够确定吗？
              ├─ 是 → 归回37个职业组
              └─ 否 → Z99其他/待分类
```

例如：

|原始标题|处理过程|最终职业组|
|---|---|---|
|急聘 Java 后端开发工程师（杭州）|标准化后命中“Java、后端、开发”规则|`D01` 软件开发|
|仓管/库管|“库管”是已确认别名，精确匹配|`P04` 物流仓储与运输调度|
|招聘专员（双休）|去掉“（双休）”，命中招聘规则或别名|`M02` 人力资源|
|技术员|没有专业方向；即使与某个官方职业名称字面接近，也不强行归类|`Z99` 其他/待分类|

## 三、37个职业组仍是主分类

详细类别和边界沿用`docs/occupation_id两层分类与关键词规则_v0.1.md`。其中第一层为10个大类，第二层为37个职业组。

这不是随意的“自己编分类”。它按岗位的**主要工作职能**分类，而不是按公司所属行业、岗位是否涉及AI、工资高低或学历要求分类。例如：

- 医药代表属于销售，而不是医疗健康；
- 房地产会计属于财务，而不是房地产；
- 新能源销售经理属于销售，而不是能源技术；
- 销售工程师属于销售；
- 建筑项目经理属于建筑工程，而不是一般项目管理。

这样做的好处是：同一种工作即使换了行业，仍然可以放进同一个职业组；同时职业分类不会把AI技能变量本身带进来。

## 四、职业大典在新方案里如何使用

职业大典不再是“最终答案库”，而是职业名称词典的一个来源。

我们建立一个可检查的“职业名称词典”，每一行都是一个常见岗位名称或职业名称，并事先标明它应归入哪个37组：

|字段|含义|
|---|---|
|`anchor_title`|用于匹配的标准岗位名称，例如“仓库管理员”“招聘专员”|
|`occupation_id`|应归入的37组代码，例如`P04`、`M02`|
|`occupation_name`|37组中文名称|
|`anchor_source`|来源：现有关键词、职业大典、人工确认或高频标题复核|
|`review_status`|是否已由项目成员确认|

词典中的名称只可来自以下四类：

1. 原关键词规则已经高置信度识别的完整岗位名称；
2. 职业大典中含义明确、能够**唯一**归入某个37组的职业细类名称；
3. 2022年高频未分类岗位，经人工确认后的标准写法；
4. 人工确认的常见简称和同义写法，例如“仓管→仓库管理员”。

不能让程序把低分匹配出的名字自动写入词典，否则错误会被不断放大。

## 五、具体分类步骤

### 第一步：岗位名称标准化

原始`招聘岗位`永远保留；只额外生成`job_title_normalized`。标准化包括：

- 统一中英文符号、大小写和空格；
- 删除“急聘、诚聘、高薪、校招、招聘3人”等广告词；
- 删除可以确认的城市前后缀；
- 删除“初级、高级、资深”等只表示职级的词；
- 统一常见写法，例如“人资→人力资源”“品质→质量”“安卓→Android”；
- 不删除决定职业含义的词，例如“销售工程师”“产品经理”“总经理助理”。

### 第二步：优先使用原关键词规则

对标准化标题运行现有规则。规则不仅有关键词，也有排除词和优先级：

- “建筑项目经理”优先归建筑工程；
- “ERP实施项目经理”优先归IT实施；
- 一般“项目经理”才归项目管理；
- “软件测试”归软件测试，不因“质量”二字归质量检验；
- “医药代表”归销售，不因“医药”二字归医疗健康。

如果标题命中明确且不冲突的规则，直接采用这一结果。模糊匹配不能推翻高置信度规则。

### 第三步：精确匹配职业名称词典

只处理第二步没有分类或规则冲突的标题。若标准化标题与词典名称、确认别名完全一致，直接归入该名称对应的37组。

这一环节通常比模糊匹配更可靠，也是提高覆盖率的主要方式。

### 第四步：模糊匹配只用于补漏

仍未归类的标题，才使用RapidFuzz的Levenshtein字符串相似度，与职业名称词典中的`anchor_title`比较。

程序不只保存“第一名”，还会保存：

- 得分最高的候选职业组；
- 第一名分数；
- 第二名职业组和分数；
- 两者分差；
- 实际匹配到的职业名称。

初步自动采用标准为：第一名分数不低于90分，且比第二名至少高5分。80—89分进入人工抽查，不自动写入正式职业变量；低于80分保留为`Z99`。

之所以不直接使用论文中的80分，是因为论文匹配的是职业细类、样本规模和训练方式也不同。我们的阈值必须由本项目的人工复核结果决定，而不能照搬。

### 第五步：保留不确定性

以下标题通常不能仅凭名称准确判断，应宁可留在`Z99`：

- 只有职级或泛称：专员、经理、主管、工程师、技术员；
- 多职能拼接且没有主次：行政人事兼销售、运营兼客服；
- 明显需要行业或职位描述才能判断的岗位；
- 第一名和第二名候选很接近的模糊匹配。

`Z99`不是“无用数据”，而是“目前不能可靠分类”的诚实标记。回归时可保留它作为一个职业组，并在稳健性检验中剔除或单独报告。

## 六、最终需要生成哪些字段

基准回归只需要较少、易懂的字段：

|字段|是否进入基准回归|作用|
|---|---|---|
|`occupation_l1`|可选|10个职业大类，用于描述统计|
|`occupation_id`|是|37个职业组代码，职业固定效应|
|`occupation_name`|否|让人能看懂代码对应哪类工作|
|`occupation_method`|否|`rule`、`exact_alias`、`fuzzy_anchor`或`unclassified`|
|`occupation_score_top1`、`occupation_score_margin`|否|检查模糊匹配是否可靠|
|`occupation_review_flag`|否|标记需要人工复核的记录|

职业大典的小类和细类代码暂不进入基准回归。将来要研究“职业AI暴露度”时，应只对能够可靠匹配官方职业代码的岗位另做匹配；如果需要形成37组层面的指标，也应按组内岗位构成加权汇总，不能把一个37组生硬地等同于单一官方职业代码。这属于扩展分析，不与当前主线混在一起。

## 七、怎样判断方案是否可用

不能只看“命中率”。高覆盖率但大量误分，比保留少量`Z99`更糟。

2022年试运行时，应分层抽取人工复核样本：

- 关键词直接分类的记录；
- 精确别名匹配的记录；
- 高分模糊匹配的记录；
- 规则与模糊结果冲突的记录；
- 保留为`Z99`的记录。

每条只需由项目成员判断一句话：**它是否确实属于程序给出的37组？如果不是，应该属于哪组，还是应保留为Z99？**

验收时同时报告：

1. 总体覆盖率；
2. 每种分类方式的人工正确率；
3. 各职业组的样本量；
4. `Z99`占比；
5. 最常见的错误和修正规则。

通过人工复核后，才把规则冻结为正式版本，并对2018—2025年全量数据运行。

## 八、这和参考论文的关系

参考论文的有用经验是：不要只靠人工肉眼读岗位名称；应建立标准名称库、做文本标准化、保存相似度分数，并让职业匹配过程可以复核。

本项目不照搬其“直接把岗位匹配到职业大典细类，再做模型训练”的做法。原因是我们的当前目标是形成稳健、容易解释的基准回归职业固定效应；2022年试跑也显示，直接使用过细职业小类会降低有效覆盖率。

因此，v0.3吸收的是它的**标准化和模糊匹配思想**，而不是把其细分类层级照搬过来。

## 九、2022年试运行结果

2022年328,548条招聘广告已按本方案试运行：

|结果|记录数|占比|
|---|---:|---:|
|原关键词规则分类|231,619|70.50%|
|职业名称词典精确补漏|706|0.21%|
|高分模糊补漏|121|0.04%|
|最终分类合计|232,446|70.75%|
|`Z99`其他/待分类|96,102|29.25%|

与v0.1相比，v0.3新增827条分类记录。这个提升不大，但符合预期：严格模糊匹配的作用是补充“Android应用开发工程师—Android开发工程师”这类近似写法，而不是把“技术员、研发工程师、管培生”等信息不足的岗位硬分进去。

本次输出与`confirmed_core_v2`逐条对应，职业代码和分数阈值均通过独立程序验证。高分模糊匹配121条全部标记为待人工抽查；另有4,680条处于80—89分复核区间，尚未写入职业变量。

## 十、执行顺序

1. 保留v0.1的10大类、37职业组和关键词优先级；
2. 建立并人工确认第一版“职业名称词典”；
3. 仅对v0.1未分类或冲突标题运行精确/模糊匹配；
4. 在2022年试跑，并输出覆盖率、审核样本和典型错误；（已完成）
5. 项目组根据人工复核调整词典、阈值和少量关键词；
6. 冻结规则版本后，才运行2018—2025年全量数据。

在第5步完成前，任何职业分类结果都不直接并入正式回归底表。
