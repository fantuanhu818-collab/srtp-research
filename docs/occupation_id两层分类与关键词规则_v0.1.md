# `occupation_id`两层分类与关键词规则方案 v0.1

状态：2022年试运行已完成，规则待项目组讨论；尚未运行其他年份

制定日期：2026-11-16

适用底表：`D:\SRTP\工作数据\features\confirmed_core_v2`

原始字段来源：`D:\SRTP\工作数据\curated\cleaned_v1`

## 一、方案目标

本方案用于构建基准回归中的职业固定效应变量`occupation_id`。它要解决的问题是：不能把软件工程师、销售人员和行政人员直接放在同一种职业中比较，但也不能把约218万个不同写法的岗位名称分别当成职业。

第一版采用透明、可人工检查的两层分类：

- 第一层`occupation_l1`：10个职业大类，用于描述统计、检查分类结构和稳健性分析；
- 第二层`occupation_id`：37个实质职业组，加1个`Z99其他/待分类`，是基准回归职业固定效应的候选主口径；
- 分类规则以`招聘岗位`为主，`初级分类`和`招聘类别`只在严格条件下辅助；
- 第一版不使用职位描述、AI技能词典或`ai_skill`分类结果。

本文件先固定讨论口径。项目组确认后，选择一个年度试运行，根据误分、漏分和样本分布修改规则，再决定是否全量运行。

## 二、最重要的研究约束

### 1. 职业和AI技能必须分开

`occupation_id`回答“这是什么工作”，`ai_skill`回答“这份工作是否明确要求AI技能”。职业分类不能专门设置“AI职业”，也不能因为标题含`AI、人工智能、大模型、智能化`就自动归入算法岗位。

示例：

|原始岗位|职业分类|说明|
|---|---|---|
|AI产品经理|产品管理|根据“产品经理”分类，不设AI产品类|
|智能客服专员|客户服务/售后|“智能”不改变客服职能|
|AI销售顾问|销售|按销售职能分类|
|机器学习工程师|算法与数据科学|“机器学习工程师”本身是明确职业名称|
|人工智能工程师|仅凭该名称不强制归算法类|需要其他明确职能词，否则进入待分类|

### 2. 职位描述不参与第一版分类

职位描述同时包含技能要求、工作任务和公司宣传。如果用职位描述判断职业，容易把AI技能要求或通用能力混入`occupation_id`。因此v0.1只使用岗位名称；职位描述最多用于后续人工复核，不进入自动规则。

### 3. 行业不等于职业

`新能源、房地产、银行、医药`是行业或业务场景，不足以单独判断职业。例如“新能源销售经理”仍是销售，“医药代表”仍是销售，“房地产会计”仍是财务。

## 三、两层职业分类

第二层代码一经用于回归就不随意改名或复用。需要合并、拆分时提升规则版本。

本方案采用“主要工作职能”作为分类标准，而不是行业、公司、技能数量或职级。具体判断顺序是：

1. 岗位日常主要承担什么职能；
2. 该职能能否跨行业保持相同含义；
3. 分类是否能与AI技能要求独立；
4. 类别边界能否用岗位名称规则解释并由人工复核；
5. 同一规则能否稳定应用于2018—2025年。

这是一套为本项目职业固定效应设计的研究分类，不宣称等同于国家职业分类代码。后期如需与外部职业AI暴露度连接，应另做本分类到权威职业代码的映射，不能把当前代码直接当作官方职业代码。

## 四、分类使用的字段

### 1. 主字段：`招聘岗位`

所有高置信度分类都必须能从岗位名称本身找到依据。

### 2. 辅助字段：`初级分类`

只有在以下条件同时满足时才能辅助分类：

- 岗位名称没有命中高置信度规则；
- 该年度的`初级分类`不是“全职、实习、校园、其他”等用工或无意义标签；
- 辅助值能唯一对应本方案中的一个职业组；
- 结果标记为中或低置信度，不能与岗位名称明确含义冲突。

### 3. 辅助字段：`招聘类别`

现有数据中该字段大量是“全职”或行业名称，因此默认不参与分类。只有出现明确职能链条，如`项目助理<经理助理_文秘`，且岗位名称信息不足时，才可作为低置信度回退证据。

### 4. 第一版明确不用的字段

- `职位描述`；
- `上市公司行业`；
- `企业名称`；
- AI技能识别结果；
- 工资、学历、经验和城市。

这些字段可用于检查分类分布，但不能决定职业类别。

## 五、岗位名称标准化规则

标准化只生成新字段`job_title_normalized`，不得覆盖原始`招聘岗位`。

依次执行：

1. Unicode NFKC规范化，统一全角/半角字符；
2. 英文字母统一为小写，连续空白压缩；
3. 统一括号、斜杠、连接号等符号；
4. 删除纯招聘噪声，如`急聘、诚聘、高薪、直招、校招、社招、若干名、招聘3人`；
5. 删除明确的地点前后缀，如`北京-会计、会计（杭州）`，但必须来自城市词表；
6. 删除纯职级修饰，如`初级、中级、高级、资深、助理级`，但不能破坏固定职业短语；
7. 保留能决定职能的完整短语，如`产品经理、客户经理、项目经理、总经理、销售工程师`；
8. 括号内容不一律删除。只有括号内容被确认是地点、编号、招聘人数或公司部门时才删除；`会计（成本核算）`中的“成本核算”应保留。

标准化后的空字符串或只剩“专员、经理、主管、工程师、助理”等泛职级词时，不强行分类。

## 六、关键词规则结构

每条机器规则必须至少包含：

|字段|含义|
|---|---|
|`rule_id`|稳定规则编号，例如`D03_001`|
|`occupation_id`|目标第二层职业代码|
|`include_pattern`|必须命中的完整词或正则表达式|
|`exclude_pattern`|出现后不能使用该规则的词|
|`priority`|冲突时的优先级，数值越小越优先|
|`match_type`|完整短语、组合条件或辅助字段回退|
|`confidence`|高、中、低|
|`example_positive`|应命中的示例|
|`example_negative`|不应命中的示例|

不允许只维护一个没有排除词和优先级的“关键词列表”。

## 八、优先级和冲突处理

### 1. 总体优先级

按以下顺序执行：

1. 完整职业短语规则；
2. 专业技术组合规则；
3. 明确职能关键词；
4. `初级分类`辅助规则；
5. `招聘类别`辅助规则；
6. 其他/待分类。

### 2. 完整短语优先于通用词

|岗位|正确分类|原因|
|---|---|---|
|销售工程师|B01销售|完整短语优先于“工程师”|
|测试开发工程师|D04软件测试|完整短语优先于“开发”|
|产品经理|B04产品管理|不能因“经理”归高级管理|
|生产经理|P01生产制造|不能因含“产…经理”误判为产品经理|
|总经理助理|M03行政支持|完整短语优先于“总经理”|
|财务经理|F01财务会计|职能经理不属于高级经营管理|
|建筑项目经理|C01建筑土木|专业领域项目优先于通用项目管理|
|ERP实施顾问|D06 IT实施|实施职能优先于一般咨询|
|数据产品经理|B04产品管理|产品管理职能优先，数据仅是业务对象|
|数据运营|B05业务运营|运营职能优先于数据分析|
|机械设计工程师|E01机械电气|专业工程设计不归视觉创意设计|
|医药代表|B01销售|固定职业短语，本质是销售|

### 3. 多职能岗位

- 有固定复合职业含义时按固定规则，如`人事行政专员 → M02`；
- 有主次结构时按主职能，如`销售兼客服`且标题主语为销售，可归B01并记录次要命中；
- 两个职业并列且无法判断主次，如`行政/财务专员`，归`Z99`并标记`ambiguous_multi_function`；
- 不允许按关键词在字符串中出现的先后顺序随意决定。

### 4. “经理、主管、工程师、专员”不能单独分类

这些词本身主要反映职级或通用岗位形式，必须和职能词组合。只写“经理”“工程师”“专员”的岗位进入`Z99`。

## 九、置信度和后台审核字段

正式进入模型的研究变量只有第二层`occupation_id`。为方便交接和修正规则，特征文件同时保留以下审核字段，但它们不算论文研究变量：

|字段|用途|
|---|---|
|`occupation_l1`|第一层职业大类代码|
|`occupation_name`|第二层中文名称|
|`job_title_normalized`|标准化岗位名称|
|`occupation_rule_id`|最终采用的规则编号|
|`occupation_match_text`|实际命中的短语|
|`occupation_source`|`job_title`、`primary_category_fallback`或`recruitment_category_fallback`|
|`occupation_confidence`|high、medium、low、unclassified|
|`occupation_secondary_hits`|未被采用的其他类别命中，用于检查冲突|

置信度定义：

- `high`：岗位名称命中唯一的完整职业短语或高识别度组合规则；
- `medium`：岗位名称命中明确职能词，但存在一定泛化，或岗位名称与辅助分类一致；
- `low`：主要依赖经审核后的辅助分类；
- `unclassified`：无可靠依据或多职能冲突，`occupation_id = Z99`。

## 十、一年试运行的输出和验收

### 1. 试运行输出

- 年度职业分类特征Parquet；
- 各职业组记录数和占比；
- 第一层、第二层、置信度和规则来源分布；
- 未分类高频岗位名称前200项；
- 多类别冲突高频岗位前200项；
- 每条规则的命中数量；
- 分层人工复核样本CSV。

### 2. 人工复核样本

第一轮建议抽取600—800条：

- 每个第二层职业组至少抽取10—15条；
- 高频职业组额外抽样；
- `Z99`和低置信度记录重点抽样；
- 多类别冲突记录重点抽样；
- AI技能线完成后，再比较AI命中与非AI命中样本的职业误分率，但AI结果不反向决定分类。

两名项目成员可以分别标注一部分共同样本，记录“正确类别、建议类别、错误原因”。

### 3. 第一轮验收目标

- 非缺失岗位名称的自动分类覆盖率目标不低于90%；
- 高、中置信度合计目标不低于85%；
- 人工复核总体准确率目标不低于90%；
- 高频职业组不得存在明显系统性误分；
- `Z99`占比原则上不高于10%，但不能通过强行分类压低；
- 某一职业组样本过少或边界无法解释时，优先合并而不是保留空壳类别；
- 必须分别报告各年份分类覆盖率，不能只报告全样本总覆盖率。

这些是试运行目标，不是脚本为了通过而必须硬编码的门槛。未达到时应查看切片并改规则。

## 十一、版本控制和修改方式

1. v0.1方案确认后生成机器可读规则表，不把规则散落在Python代码中；
2. 规则表、程序、输出和人工复核报告使用相同版本号；
3. 每次增加、删除或调整关键词，都记录修改原因和影响记录数；
4. 已用于回归的代码含义不得静默改变；
5. 一年试运行通过后才生成2018—2025年全量`occupation_id`；
6. 全量运行后仍要按年份检查分类漂移。

## 十二、试运行前需要项目组确认的事项

1. 是否接受当前10个第一层大类、37个实质职业组和`Z99其他/待分类`；
2. 是否接受第一版把硬件、电子、嵌入式暂并入E01，并在试运行后决定是否拆组；
3. 通用`项目经理`保留独立组，还是按专业领域尽量分流；
4. `产品运营`默认归产品管理还是业务运营；
5. 低置信度辅助字段分类是否进入基准样本，还是只用于补充分析；
6. 选择哪一个年度作为首次试运行。

本方案给出的初始建议是：硬件电子暂并入E01；通用项目经理保留M04、专业项目经理优先进入专业组；`产品运营`默认归B05，只有明确承担产品设计和产品决策时才归B04；低置信度和`Z99`先保留在数据中，基准结果与“仅高/中置信度样本”结果并列做稳健性检查，不因分类困难直接删除记录。

以上事项确认后，更新机器可读规则版本并重新试跑2022年；在2022年规则和人工复核通过前，不运行其他年份，也不修改`confirmed_core_v2`。

## 十三、2022年试运行状态

2022年328,548条记录已经按本方案试运行，最终分类覆盖率70.50%，`Z99`占29.50%，尚未达到正式回归要求。规则已转为机器可读JSON，试运行输出未合入`confirmed_core_v2`。具体问题、典型切片和下一步建议见`outputs/qc/occupation_pilot_2022_report.md`。
