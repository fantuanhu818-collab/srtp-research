# 2022年`occupation_id`试运行报告

运行日期：2026-11-16

规则版本：`occupation_rules_v0.1`

## 一、结论

2022年职业分类试运行已经完成，程序和输出结构通过独立复核，但当前结果**还不能直接作为正式基准回归的职业固定效应**。

- 输入记录：328,548条；
- 成功归入37个实质职业组：231,619条，占70.50%；
- `Z99其他/待分类`：96,929条，占29.50%；
- 其中无规则命中：88,618条，占26.97%；
- 同优先级规则冲突：8,311条，占2.53%；
- 高置信度：217,643条，占66.24%；
- 中置信度：13,825条，占4.21%；
- 依赖`初级分类`回退：151条，占0.05%；
- 输出记录与`confirmed_core_v2`逐条一一匹配，独立验证通过。

方案原定覆盖率目标为90%，本次只有70.50%。继续机械增加少量关键词不能解决主要问题，需要项目组先决定通用岗位、复合岗位和长尾岗位的处理路线。

## 二、试运行做了什么

1. 只读取2022年`招聘岗位`，不使用职位描述、AI技能、行业或工资决定职业；
2. `初级分类`只在岗位名称无命中时作为回退；
3. `招聘类别`不参与自动判断；
4. 按完整职业短语、专业组合、职能关键词、辅助字段回退的顺序分类；
5. 同一优先级命中两个职业组时不强行选择，进入`Z99`并保存全部冲突证据；
6. 输出800条分层人工复核样本，但尚未进行人工标注，因此目前不能报告真实分类准确率。

## 三、辅助分类字段在2022年几乎不可用

2022年：

- `初级分类`有318,681条写成“全职”，另有“校园、兼职/临时、实习”等非职业值；
- `招聘类别`有324,930条为空，其余大量是“医药制造、新能源、互联网”等行业；
- 最终只有151条依靠`初级分类`回退完成，占0.05%。

因此，不能指望现有两个分类字段补足岗位名称规则，也不能直接把它们作为统一职业编码。

## 四、长尾岗位是主要障碍

2022年共有156,240种标准化岗位名称。`Z99`中仍有57,515种不同名称：

|Z99岗位名称出现次数|不同名称数|涉及记录数|
|---:|---:|---:|
|1次|46,667|46,667|
|2次|6,444|12,888|
|3—5次|2,730|9,847|
|6—10次|867|6,411|
|11—50次|751|15,027|
|51次以上|56|6,089|

高频未分类岗位前300种合计只有13,674条。也就是说，即使逐个补完前300个高频岗位，仍会留下大量只出现一两次的长尾名称。关键词规则可以继续改善，但仅靠人工追加高频词很难达到90%覆盖率。

## 五、需要讨论的岗位类型

### 1. “测试”不能自动等同于软件测试

典型未分类值：

- `测试工程师`448条；
- `硬件测试工程师`280条；
- `硬件测试`109条；
- `测试经理`102条；
- `系统测试工程师`93条；
- `可靠性测试工程师`56条。

问题是“测试”可能指软件测试、硬件验证、产品质量检验或实验检测。建议不要全部塞入D04软件测试。

建议选择：

- 新增“通用测试与验证”职业组，领域明确时再分流到D04或P02；或
- 保持`Z99`，后续使用职位描述中的工作任务做第二阶段判断。

### 2. 通用研发与技术岗位缺少专业方向

典型值包括`研发工程师`442条、`技术员`151条、`研发助理`68条、`研发经理`66条、`技术研发工程师`62条等。

方案中的E03本来包含“其他技术研发”，可以把明确写有“研发”的岗位以中置信度归入E03；但这些岗位实际可能属于软件、机械、电子、化工或医药。这样做能提高覆盖率，却会形成较宽的混合职业组。

### 3. 管培生和储备干部不是稳定职业

`管培生`253条、`储备干部`238条、`生产储备干部`132条、`管理培训生`112条。它们表示培养计划或职级状态，不说明最终工作职能。

建议继续保留在`Z99`，不要单独把“管培生”当作具有共同工作内容的职业。

### 4. 复合岗位需要统一“主职能”原则

当前同优先级冲突8,311条。典型例子：

|岗位|冲突类别|需要确定的原则|
|---|---|---|
|污水处理操作工|环境工程 / 生产操作|行业领域优先还是实际动作“操作工”优先|
|销售行政专员|销售 / 行政|服务销售部门是否仍算销售|
|制程品质工程师|生产工艺 / 质量|质量监督是否优先|
|化工设备工程师|化工 / 设备工程|专业领域还是工程职能优先|
|售后服务维修工程师|客服售后 / 维修|客户服务还是现场维修优先|
|销售培训师|销售 / 教育培训|服务对象还是实际工作任务优先|
|品牌运营经理|品牌市场 / 业务运营|品牌职能还是运营职能优先|

建议总体采用“实际主要任务优先”：操作、维修、检验、培训等任务词优先于行业修饰词；但销售行政、销售会计等支持岗位应按实际专业职能分类，而不是因为服务销售部门就归销售。

### 5. 部分岗位名称信息本身不足

如`统计员、区域经理、城市经理、技术工程师、工程主管、综合管理员、计划员`。即使人工看到标题，也无法可靠判断属于哪个职业。对这些值强行分类只会制造看似完整的错误编码。

## 六、规则运行中已经修复的问题

本轮共迭代三次：

|阶段|分类覆盖率|Z99占比|同优先级冲突|
|---|---:|---:|---:|
|初始规则|59.79%|40.21%|10,262|
|修正标准化和正则边界|67.15%|32.85%|8,707|
|补充明确职能与复合短语|70.50%|29.50%|8,311|

已修复的典型技术错误：

- 不再把`招聘专员`削成只有“专员”；
- `自动化工程师`不再因连续字符“化工”误命中化工类；
- `实施工程师`不再因包含“施工”误命中建筑类；
- `信息安全工程师`不再因“安全工程师”误命中生产安全；
- `数据库管理员`不再因包含“库管”误命中仓储；
- `建筑机电工程师`不再因包含“电工”误命中普通生产工人。

## 七、下一步建议

建议不要直接全量运行2018—2025年。先完成以下两步：

1. 项目组确认本报告第五节的五类口径，尤其是测试、通用研发和复合岗位；
2. 对`occupation_pilot_2022_review_sample.csv`中的800条样本进行人工复核，至少先共同复核200条，计算各职业组的误分情况。

如果仍坚持只用关键词，比较现实的做法是：

- 保留当前高/中置信度分类；
- 对明确的通用研发和测试岗位增加少数过渡职业组；
- `Z99`继续作为独立组，不为了覆盖率强行归类；
- 回归时同时报告全样本结果和排除`Z99`/低置信度后的结果，并说明后者存在样本选择风险。

如果希望覆盖率接近90%，建议增加“第二阶段标题分类器”：用人工标注样本训练只读取岗位名称的字符级模型，并设置概率阈值；低概率记录继续留在`Z99`。该模型不能读取职位描述或AI变量，以免与`ai_skill`发生信息泄漏。此方案比继续无限扩充关键词更适合处理数万种低频岗位，但需要额外人工标注与验证。
